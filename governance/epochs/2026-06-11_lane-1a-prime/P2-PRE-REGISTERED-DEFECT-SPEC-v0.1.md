## 2. Purpose

Name the single exact defect the constructed-positive would carry, in the D4 task's own terms, pre-registered before any construction, so that a future instrument's elimination of the defective member can be attributed to *this* defect and nothing else.

## 3. Claimed concept

> The defective member differs from the clean member by exactly one controlled property: **the queried key's value is not constructible from the listed pairs** — the key named in the Query line does not appear as a left-hand entry in any pair, so no listed pair supplies its value — while the surface form remains indistinguishable from an answerable item.

In D4 terms: a clean answerable item is `Pairs: {k_i -> v_i}; Query: k_j` where `k_j ∈ {k_i}`, so the gold value `v_j` is present in the list. The defect removes that guarantee: `k_j ∉ {k_i}`, so there is no listed value for the queried key. The item still *looks* answerable (same format, same length, a plausible query token), but its answer is **not constructible from the context**.

The pre-registered elimination ground: a correct instrument should eliminate this item because no correct answer is derivable from the given pairs — a competent candidate must abstain or fail, and a candidate that confidently "answers" is producing an ungrounded token. The clean member, whose queried key *is* present, should be answerable and should not be eliminated. The verdict contrast (defective eliminated, clean spared) is what would distinguish real-candidate elimination from the other firing types.
