# Passdown Letters

Date-stamped CS-Engineer letters capturing the state of the program at the close of each
session. Each letter is a self-contained "where things stand right now" snapshot — what
just happened, what's pending, what's blocked, and what to read next.

## Convention

- Filename: `YYYY-MM-DD_passdown-letter.md`
- One letter per passdown event (typically the end of a working session or when a major
  state change lands).
- Read the **most recent** letter first. Sort the directory alphabetically — because of
  the `YYYY-MM-DD_` prefix, alphabetical = chronological.
- A new CS reads only the most recent letter + the standing docs
  (`ONBOARDING-CS.md`, `governance/standing/`); older letters are historical context.
- Old letters are **not** deleted. The directory accumulates as the program runs.

## Why this exists

A new CS Engineer (human or AI) should be able to bootstrap in ~10 minutes by reading
exactly one passdown letter. Reading the full governance archive cold would take hours,
and most of it is historical. The passdown letter cuts that cost to a single document.

## What a passdown letter contains

- **Current state**: paper-by-paper, lane-by-lane status as of this date.
- **What just happened**: deliverables from the most recent session(s).
- **What's pending for CS**: any open items CS owns going forward.
- **What's blocked and why**: which non-authorizations are in force; what would unblock
  each.
- **Open questions / decisions awaiting actors**: items waiting on Manager / Team Lead /
  Senior.
- **Read next**: 3–5 specific documents a new CS should review beyond this letter.

## When to write a new one

- After any merge or lock event.
- After any paper release, addendum, or readiness check.
- After any Manager authorization that materially changes the open board.
- At the explicit close of a working session (Manager instruction).

If unsure, write one. They're cheap; they age well.
